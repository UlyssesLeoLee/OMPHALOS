# 02 基本設計書

## 1. 設計方針
単体ローカルプロセスを基軸に、外部AIモデルへの常時依存を設けない。要件定義だけに管理境界を置き、基本/詳細設計・コードは監視対象の証拠。分配は宿主プラグイン、入出力はCLI/MCP、ポリシーの最終ゲートはGit保護ブランチ。

## 2. 構成
1. `Parser`：要件ソースから条項ID、本文、SHA256、行を抽出。
2. `Baseline Store`：pending.json、approved.json、SQLite index/cache、audit.jsonl。
3. `Comparator`：CJK n-gramと英数字トークンによる候補選定、否定規則による衝突候補判定。
4. `Hook Adapter`：UserPromptSubmit、PreToolUseを処理し、宿主固有応答形式を生成。
5. `MCP Adapter`：stdio経由で4ツールを公開。
6. `Git Scanner`：差分追加行から候補乖離を検出。
7. `CI`：承認済み要件とワークツリーの一致、ブランチ変更の候補審査。

詳細図：`../architecture/01_components.mmd`。

## 3. 論理データ
- `Requirement`：id/source/section/line/content/digest/constraints。
- `Baseline`：schema_version/project/digest/approved_at_utc/requirements。
- `Assessment`：outcome/action/summary/hits/options/evidence_kind/baseline_digest。
- `Audit`：kind/epoch/payload/previous_hash/chain_hash。
- SQLite：`req_index`, `cache`, `req_fts`（任意加速）。
ER：`../architecture/02_er.mmd`。

## 4. 業務・システムフロー
導入：存在する要件文書を設定→ `init`（未批准候補）→人間 `approve`→approved.jsonを保護ブランチに登録。
新入力：Hook→基線検証→局所トークン検索→判断→少数の該当条項を注入、または討議阻断。
コード変更：Git差分→関係候補→実装が要件から乖離していないか確認。候補は根拠不足の可能性を明記。
要件変更：編集提案→差分確認→新pending→正式批准→新baselineをPRでレビュー。
フロー図：`../architecture/03_prompt_sequence.mmd`、`../architecture/04_decision_state.mmd`。

## 5. 安全境界
(1) ローカルTTYの人間確認は**単独の本人認証ではない**。(2) MCP提案は承認ではない。(3) Shellによる変更はHookのヒューリスティック検知を回避できる。(4) protected branch、CODEOWNERS、required CIが必須。(5) 要件原本変更とapproved.jsonの双方変更にはオーナー審査を必須にする。

## 6. 画面/対話設計
通常は完全に無表示。候補乖離で初めて以下を最大3件提示：要件IDと出典/行、要件原文抜粋、ユーザー指示/コード差分、衝突理由、推奨A/B/C/D。具体的行番号を検証できない場合は「所在不明」と明示。

## 7. 障害時
要件ファイル欠落/未批准/パーサエラー：Hookコマンド非0、宿主でfail-closed。SQLite FTS5構築失敗：コア比較はインメモリ候補検索にフォールバック。MCP障害：そのMCP呼び出しに依存した承認は禁止。Git差分を取れない場合：CI失敗。

## 8. デプロイ先
Windows 11/Linux/macOSのRust CLI。標準入出力MCP、IDE/AgentのHook。データは既定でプロジェクトルート下 `.concept-guard/`、機密データを外部送信しない設計。
