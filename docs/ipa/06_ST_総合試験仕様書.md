# 06 ST 総合試験仕様書

## 目的
実運用に近いシナリオで要件のみが統制され、低コストで毎ターン自動チェックが機能することを確認する。

| ID | シナリオ | 期待結果 | 注意点 |
|---|---|---|---|
| ST-001 | 2000+一般設計文書+3件の現行要件を設置 | 一般設計文書は監視対象にならず要件だけに紐付く | 検索性能計測 |
| ST-002 | 既存要件と一致する改善指示を連続送信 | 毎回モデルAPI0回で処理 | Hook注入Token測定 |
| ST-003 | 要件禁止事項に反する新指示 | 3件以内の根拠と選択肢を表示し停止 | 不要な会話継続を避ける |
| ST-004 | 利用者が「前案は実験」と発言 | Concept討議、批准までは要件変更なし | 人間思想の未観測部分は推測しない |
| ST-005 | 外部IDEが要件を変更 | 次のcheck-baseline/CIで検出 | Hook自体で捕捉できない変更を想定 |
| ST-006 | 別branchで要件とapproved.json両方変更 | Ownerレビューなしでマージ不可 | CIだけでは改竄防止不可 |
| ST-007 | 複数Agentが別branchで相反する提案 | 同一のApprovedを参照、無断更新不可 | 並行実行 |
| ST-008 | MCP接続不可/Hookタイムアウト | 失敗時に書込みを許可しない | 宿主依存検証 |
| ST-009 | 日本語・中国語・英語の曖昧要件 | 不確実性を明示、勝手に確定しない | LLM未搭載の限界を記録 |
| ST-010 | 附属モデル/CIを迂回しようとする操作 | 保護PR/承認者審査を要求 | 管理者による直接pushは別リスク |
| ST-011 | 既存要件を改訂して正式批准 | 旧版をGit履歴として保全、後続比較に新基線を使用 | Ownerレビュー必須 |
| ST-012 | 2200文書でTokenベンチマーク | 実測値に基づきNFR評価 | 目標未達の場合は要改善 |

## 指標
関連要件Top3 Recall、偽ブロック率、候補衝突Precision、重大違反見逃し率、1ターン上乗せToken、p50/p95遅延、CI false fail率、Hook bypass検出率。合格値は**本番対象の履歴データでオーナーが設定**し、根拠のない95%などの固定目標を捏造しない。

## 実施体制
テスト責任者、要件権限者、各宿主の管理者、CI管理者が互いの役割を分ける。結果、時刻、branch、commit、環境、期待と実際、スクリーンショット/ログを記録。
