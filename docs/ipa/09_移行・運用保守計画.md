# 09 移行・運用保守計画

## 導入手順
1. 既存要件定義文書の場所・責任者を確定。新規生成はしない。
2. UTF-8 Markdown/TXTへの変換が必要なものは**原本との対応表**（原ファイルハッシュ、頁・シート・セル、変換日時）を保存する。変換結果を即座に承認せず内容検証する。
3. `concept-guard setup`→`config.toml`へ要件パス→`init`。必ず人間が候補条項を確認する。
4. `approve` により基線作成。Gitに要件ソースと approved.jsonを登録。GitHub branch rules/required CI/CODEOWNERSを設定。
5. Agentが参照するPluginを私有インストール。Hook trust確認、MCP4ツール検査。
6. UATとセキュリティ/性能テスト後に正式運用する。

## 日常運用
- 通常指示：UserPromptSubmit Hookから自然に処理。
- 乖離：Hook表示の出典/指示/選択肢でConceptを議論。
- B：要件変更が必要。関連レビュー後に新基線を批准し、PRで保護承認。
- A：要件維持。コード/設計を通常開発プロセスで修正。
- C：実験として正式基線から分離。実際のbranch隔離手順はCI・branch policyを併設する。
- D：調査。根拠を追加した上で再討議。

## 障害運用
| 事象 | 検出 | 復旧 |
|---|---|---|
| Cache破損 | sqlite open失敗 | cache.sqlite削除→再構築（承認基線は維持） |
| 要件ファイル削除 | check-baseline失敗 | 削除を復旧、または正式変更審査 |
| Hook読み込まれない | 実機ITで無反応 | trust、PATH、cwd、onFailureを確認 |
| MCP接続失敗 | tools/list失敗 | server stderrを確認しRust binaryを更新 |
| 誤ブロック | 意図と根拠の不一致 | D調査、回帰ケース追加、閾値/辞書変更 |
| 監査ファイル欠損 | ログ連続性検査 | 事故票・証拠保全。必要なら外部監査ログ |

## バックアップ
Git上の要件原本と approved.json を最重要バックアップ対象にする。ディスク単体SQLiteは再生成可。データ機密に従い暗号化保存し、監査は定期アーカイブする。

## 改訂手順
Parser/Comparator変更はテストセットで想定ブロックと誤ブロックの比較を行い、SemVer及びプロトコル互換を更新する。
