# 10 変更管理・構成管理計画

## 管理対象
唯一の正式管理アンカーは**承認済み要件定義条項**。構成管理対象としてはGitコミット、Rustソース、CI/Plugin、試験証跡も保存するが、個々の基本設計/詳細設計/実装に恒久要求アンカーを強制しない。

## 変更決定の分離
- Request: 開発者の新しい指示（未批准）。
- Candidate: 実装/設計の乖離候補（自動推定・未証明）。
- Discussion: 根拠+選択肢に基づく人間とのConcept協議。
- Decision: 理由・範囲・批准者を伴う判断（MCP上の提案は決定ではない）。
- Baseline: 要件原本と同期した、保護ブランチでレビュー済みの批准版。

## 要件改訂ルート
1. 元の条項と変更案の差異を示す。
2. 変更理由、影響範囲、残留リスク、取り消し方法を簡明に示す。
3. 人間が方向性を承認し、要件ソースを修正。
4. `init`でpending作成、手元 `approve` の後、PRにapproved.jsonとソースを提出。
5. CI/Ownerレビュー完了後に主ブランチに登録。

## 権限管理
ローカルTTYでの `approve` はユーザーの物理的確認に近いが、悪意ある同権限プロセスへの認証保証にはならない。GitHub等でブランチ保護・CODEOWNERS・権限分離・監査を設定し、Agentの直接pushやHook無効化から正式要件を保護する。

## 決定記録テンプレート
```yaml
change_id: CR-2026-001
requirement_ids: [REQ-QC-001]
old_requirement_excerpt: "..."
new_concept: "..."
impact: ["業務プロセス", "実装", "テスト"]
options: ["A: 維持", "B: 改訂", "C: 実験", "D: 調査"]
selected_option: B
human_approval_reference: "PR URL / identity / time"
baseline_before: "sha256..."
baseline_after: "sha256..."
```

## リンク規則
関連文書には必要に応じ `REQ-...` を参照できるが、新たな正式アンカーとして管理しない。後続文書やコードは各開発工程で自然に更新され、正式整合性は要件に対する乖離候補検出で判断する。
