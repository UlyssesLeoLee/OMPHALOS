# 03 詳細設計書

## 1. ソース対応
| コンポーネント | 実装 | 入力→出力 |
|---|---|---|
| CLI | `src/main.rs` | argv/環境→JSON、exit code |
| 要件抽出 | `src/parse.rs` | paths/既存Markdown→Requirement[] |
| 要件台帳 | `src/store.rs` | Requirement[]→pending/approved/SQLite |
| 一致比較 | `src/engine.rs` | prompt+Baseline→Assessment |
| Hook | `src/hooks.rs` | 宿主イベントJSON→許可/拒否/短文 |
| MCP | `src/mcp.rs` | newline JSON-RPC→MCP Tools |
| 構造 | `src/model.rs` | 基本型とTOML設定 |

## 2. 要件条項抽出仕様
入力対象は明示設定 `requirements.paths` にある `.md/.markdown/.txt` のみ。階層走査にシンボリックリンク外部越境を許さない。`## [REQ-XXX] 見出し` の形式を優先し、未付番見出しにはファイルパスと見出しから `AUTO-` IDを生成。条項は次の `##` まで。重要：現MVPの見出し分割は `##`/`###`/`####` で行う。重複IDはエラー。fenced codeは読み飛ばす。UTF-8前提。

実ソース行は**見出しの行番号**、excerptは最長200文字、Hook注入は最長100文字。承認後に要件見出しを移動/変更すると自動IDが変化する可能性があるため、運用時は明示 `[REQ-...]` を推奨する。

## 3. 要件バージョン・格納
`init` は `pending.json` のみを生成し正式批准しない。`approve` は人間TTY入力 `APPROVE <digest-prefix>` と pending hash を確認し `approved.json` を出力。`check-baseline` は最新抽出結果のID/ソース/内容指紋を承認基線と比較する。承認ファイルが改ざんされた場合も内蔵digestの整合性を確認。ただし攻撃者が原本・baseline双方を書き換えられる場合、このローカル検証だけでは認証できない。サーバ側レビュー規則が必要。

SQLite表：`cache(key, assessment_json)`、`req_index(id,content,source,line)`、任意 `req_fts(id,content)`。SQLiteは検索加速/キャッシュ用途であり要件原文の権威ではない。現在の検索ランキングは Rust メモリ内、FTSテーブルは将来の最適化用に作成。

## 4. 検索仕様
- 英数字：[a-z0-9_]単語（2文字以上）。CJK：連続列から2/3文字のn-gram。
- 全文節の語出現頻度に応じ、稀な共有語は重く加算。`min_score` 以上の上位 `top_k` 最大10件を候補化。
- 手動定義 `extra_aliases` は一致時に全ての同義語を展開する。実体間対応の推論は行わない。
- `key_signal` は ASCII 技術名または3文字以上のCJK複数一致を参照。否定条項への追加意図ヒューリスティックだけを確定的ブロック候補として扱う。
- 誤判定：未登録言い換え、否定範囲、複数条件、暗黙要求、型/実行パスを理解できない。特に「compatible」を意味的完全準拠と表示しない。

## 5. Assessment I/F
```json
{
  "outcome": "conflict",
  "action": "block",
  "summary": "New request may contradict an approved MUST_NOT requirement...",
  "hits": [{
    "requirement_id": "REQ-QC-001",
    "source": "docs/requirements/qc.md",
    "line": 3,
    "section": "[REQ-QC-001] 中国侧数据导入",
    "excerpt": "- MUST_NOT: 中国侧导入时不得重复执行 OCR。",
    "score": 9,
    "reason": "New positive directive intersects..."
  }],
  "options": ["A 保持要件并调整实现", "B 讨论修订要件", "C 实验分支隔离", "D 进一步调查"],
  "evidence_kind": "user_prompt",
  "baseline_digest": "..."
}
```
`score` は確率ではない。数値を LLM confidence と表示しない。

## 6. Hook I/F と状態
### UserPromptSubmit
stdin: `{ "prompt": "...", "cwd": "...", "hook_event_name": "UserPromptSubmit" }`。
allow: `{}` または `{ "additionalContext": "REQ..." }`。
block: `{ "decision": "block", "reason": "要件ファイル:行...選択肢..." }`。
`pending_discussion.json` を作成し、討議は `讨论 Concept` または `discuss Concept` で再開。討議のみ可能で、未批准変更は不可。

### PreToolUse
stdin: `{ "tool_name": "Edit", "tool_input": { "file_path":"..." } }`。
block: `{ "hookSpecificOutput": { "hookEventName":"PreToolUse", "permissionDecision":"deny", "permissionDecisionReason":"..." } }`。
既存要件パスに対する明示的変更と未決討議中の書き込みを拒否する。Shell操作は不完全な正規表現・文字列判定であるため、**CIとの二重制御が必須**。細かい関連ファイル範囲の限定は未実装（現MVPは保守的に全書込みを遮断（Bの対象要件ソース許可だけ例外））。

### エラー
基線未作成/ソース欠損/壊れたJSONなどでCLIはexit 2とstderr。宿主側 `onFailure:block` 設定と実機動作検証が必要。Claude/Codexでイベント出力フィールドを個別確認する。

## 7. MCP (legacy initialize 互換)
Transport `stdio`、1行1 JSON-RPC 2.0、protocol `2025-06-18`。`initialize` → `tools/list` → `tools/call`、応答の`content`にJSON文字列を返す。ツール表：
| tool | 入力 | 出力 | 書換 |
|---|---|---|---|
| requirements_get | id | 承認条項/所在 | 無 |
| requirements_check | text | Assessment | cacheのみ |
| concept_discuss | 無 | 未決レビュー | 無 |
| concept_decide | option,reason | 提案であり未批准 | auditにproposal |

未知/不正 tool は `isError` またはJSON-RPC errorを返す。stdin/stdoutに診断ログを混在させない。

## 8. CLI 終了コード
成功0、不正設定/違反/未批准/未証拠2。`scan-branch`は候補乖離があれば2を返す。Git変更なしの非違反は0。無証拠の意味論証明はしない。

## 9. 決定と承認
`decision A|B|C|D --reason ...` はTTYの短い確認を要求して監査に記録。A/Cは討議待ち解除（原禁止要求の許可ではない）、Bは10分間の関連要件ソース限定編集許可を発行するが批准状態は据置。Dは据置。要件が必要なら `init`→ `approve`で新基線を準備し、必須のOwnerレビューを通してmainへ反映。承認者はCI側のポリシーで保護すること。

## 10. 性能制約
通常のPrompt比較でネットワークLLM通信ゼロ。現在の候補検索は全条項のトークン生成・ランキングを行うため件数に概ね比例する。入力と承認基線のハッシュキャッシュにより繰返しを削減。大規模化した場合、FTS prefilter採用や永続化済みtoken postings、embedding optionalを別フェーズで実施する。
