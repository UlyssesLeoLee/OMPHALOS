# 01 要件定義書（Concept Guard）

## 1. 背景・目的
継続開発で文書・実装・人間の方針が更新され、旧情報に基づく実装が再流入する。全文書に管理アンカーを付与する高コスト方式を採用せず、**現行承認済みの要件定義だけを固定アンカー**とする。各新規指示に対し自動的に関連要件を検索し、明示的な不一致は短い証拠で人間と協議する。

## 2. 利害関係者
プロジェクトオーナー（要件批准者）、人間開発者、複数AI Agent、レビュー担当、CI運用者。所有者が別である場合、批准権限とコード承認権限を明示的に分離する。

## 3. 対象範囲
対象：既存 `.md/.txt` 要件、承認スナップショット、条項 ID/内容指紋、プロンプト比較、差分候補、Hook、MCP、監査記録、CI。
対象外：基本設計/詳細設計/コードの独立アンカー・厳密な全量意味証明・未観測の思考推定・自動要件書作成・PDF/DOCX/XLSX直接解析・Web UI・汎用RAG。

## 4. 業務フロー
起動前：既存要件ソースを設定→自動条項抽出→利用者が初回批准→指紋付き baseline を記録。運用中：ユーザー指示→Hook→ローカル検索と規則比較→許可または候補乖離の短い対話→人間決定→必要に応じ要件改訂とCI承認。

| FR-003 | ユーザー新指示毎に入口Hookを実行 | P0 | 各ユーザーターンで確認 |
| FR-004 | ローカル検索と上位3条項抽出 | P0 | 発見結果に出典・行番号 |
| FR-005 | 明示禁止事項と新指示の候補衝突を検出 | P0 | OCR禁止にOCR追加が候補衝突 |
| FR-006 | 既知衝突時にHookで当該指示を停止 | P0 | Agentが矛盾指示を未承認で実行しない |
| FR-007 | 短い根拠とA/B/C/D選択肢を提示 | P0 | 3件以内の優先表示 |
| FR-008 | MCPで取得・比較・対話・提案を行う | P0 | 4ツールを発見・実行可 |

## 6. 非機能要求
| ID | 要件 | 目標/留保 |
|---|---|---|
| NFR-001 | 通常の入口比較はモデルAPIを呼ばない | 本実装では0外部LLM呼び出し |
| NFR-002 | 許可時の追加コンテキストを最小化 | 0～2条項の短い抜粋 |
| NFR-003 | ソースが欠落/基線が壊れたとき安全側 | コマンド異常、Hookはfail-closed設定が必要 |
| NFR-004 | 原本要件の意味をAIが独断修正しない | MCPは直接承認しない |
| NFR-005 | Windows/Linux/macOSでRust CLIを構築可能 | 実機評価未実施 |
| NFR-006 | 要件が日本語/中国語/英語混在可能 | CJK 2/3gram + ASCII、品質測定必須 |
| NFR-007 | 主目的は低運用コスト | 大型DB・Web UI・ベクトル検索不要 |
| NFR-008 | 重大変更の追跡性 | requirement digest + CI review + audit |
| NFR-009 | 比較結果は不確実性を明示 | `compatible`は意味的な完全適合証明でない |

## 7. 状態・判定の用語
`compatible`: ローカル規則上明示矛盾なし。`conflict`: 禁止条項に触れる強い候補。`new_requirement`: 関連要件が見つからない追加指示。`uncertain`: 十分な証拠なし。結果アクションは `allow/discuss/block`。`discuss`/`block` は操作継続を止め、A維持、B要件変更、C実験隔離、D調査を提示する。

## 8. 受入基準
- 初期デモの3条項を批准、原文改変時のチェックが失敗する。
- 新指示 `中国侧导入时新增 OCR 识别` が REQ-QC-001 の根拠付きでブロックされる。
- `移除 OCR` は同じ理由で誤ブロックされない。
- MCPが4ツールを提示する。
- 非TTYで baseline 批准が失敗する。
- Codex/Claude実機でHookの信頼と失敗設定を確認する。
- 精度指標は評価セットで実測する。すべての意味的相違を検知できるとの保証はしない。

## 9. 実装済み範囲の留保
上記は製品要件であり、MVP実装には未実装/要強化の箇所がある。実際のソースと既知の限界は D-03・D-11・D-13 を参照し、完成と混同しない。
