# 三轮对抗式自审记录（静态审查）

> 审查方法：源代码、配置、设计与要求做静态交叉检查。当前环境缺失 Rust toolchain，未执行编译、Rust UT、插件实机或 CI。因此「识别与设计修正」不等于动态验证。

## Round 1: 安全与权威来源
**质疑：** 新要件能否被Agent擅自批准？两个文件都被篡改还能否通过本地hash？
**处理：** MCP决定为 proposal_only；TTY交互批准；CI与CODEOWNERS/受保护分支成为最终门禁；明示同权限进程能伪造TTY和本地审计。本地哈希不声称可抵御恶意作者。
**残余：** 目标Git仓库Owner、required checks必须人工配置；未实机验证。

## Round 2: 低成本、正确性与误判
**质疑：** 每次是否需要全文扫描2200份文档？看到OCR调用能否断言违反？
**处理：** 索引仅要件路径；外部LLM调用为0；缓存+索引；代码差分只当候选证据，原文摘录+行号提供给人；词法规则不能代替语义证明。
**残余：** 召回率/误报率尚未实测；FTS表创建但候选排序仍靠内存；跨语言别名依赖手工补充。

## Round 3: 可部署与维护性
**质疑：** 插件Hook是否自动可信？无法运行时会不会默默放行？Pending讨论会不会锁住无关开发？
**处理：** 配置失败时在支持的宿主中fail-closed；正式合并独立CI；标注Plugin需信任；Pending期间写操作采取保守阻断；配置和API都写入操作手册。
**残余：** Codex/Claude Hook行为、Windows PATH、MCP协议仍需实机验证；Pending的全写入范围锁偏宽，建议下一版改为按影响范围判定。

## 严格交付结论
源文件与设计资料可交付审阅/继续开发。**不应标注为“通过全部测试的生产版”**。进入实际生产前，需执行 Rust 编译、全部UT/IT/ST/UAT、真实2200+库召回评估与访问控制验证。
